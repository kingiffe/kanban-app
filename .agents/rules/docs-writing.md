# 文檔撰寫規範 (Documentation Writing Guidelines)

本規範適用於本專案中所有技術文檔、說明文件（如 `README.md`）、架構說明以及代碼註解的編寫與維護。

---

## 1. 語言與語氣風格

- **主要語言**：預設使用繁體中文（台灣習慣用語，如「代碼/程式碼」、「專案」），專有名詞或英文術語可保留原文（例如 DOM、Local Storage、Event Listener）。
- **語氣基調**：客觀、專業、精確且簡潔，避免冗長或模糊不清的描述。
- **目標受眾**：假定讀者具備基本的 Web 開發背景，重點放在專案的設計邏輯、使用方式與架構細節。

---

## 2. Markdown 格式標準

- **標題階層**：
  - 每個文件僅包含一個 H1 (`#`) 作為文件主標題。
  - 嚴格遵守階層結構（H1 -> H2 -> H3），不可跳級（例如不可由 H1 直接跳至 H3）。
- **代碼區塊**：
  - 所有代碼段落均須標註語法高亮標籤（如 ```javascript, ```html, ```css, ```bash, ```json）。
  - 代碼範例應保持完整、可運行，並標註關鍵變數或配置說明。
- **列表與表格**：
  - 列舉功能或步驟時優先使用無序列表 (`-`) 或有序列表 (`1.`)。
  - 遇到對比、屬性列表或狀態說明時，使用 GFM 表格呈現。
- **連結與路徑**：
  - 引用專案檔案時使用相對路徑或標準 Markdown 連結。

---

## 3. 專案文檔結構要求

當撰寫或更新專案級說明文件（例如 `README.md`）時，建議遵循以下結構：

1. **專案簡介 (Overview)**：一句話總結專案目的與核心價值。
2. **核心功能 (Features)**：清晰列出主要功能特色（如待辦事項增刪改查、狀態篩選、本地存儲等）。
3. **技術棧 (Tech Stack)**：列出所使用的技術（如 HTML5, CSS3, Vanilla JavaScript）。
4. **快速開始 (Getting Started)**：
   - 前置需求（如瀏覽器環境）。
   - 本地執行步驟（如開啟 `index.html` 或使用靜態伺服器）。
5. **目錄結構 (Project Structure)**：樹狀展示專案關鍵檔案與用途。
6. **使用與操作說明 (Usage Guide)**：簡述使用者介面操作與流程。

---

## 4. 程式碼註解規範

- **JSDoc 格式**：核心函式應標註 `@param`、`@returns` 及簡短功能說明。
- **解釋「為什麼」而非「做什麼」**：
  - 避免顯而易見的廢話註解（例如 `i++; // i 加 1`）。
  - 重點記錄業務邏輯、邊界情況處置、跨模組依賴原因或 workaround 說明。

---

## 5. 同步與維護要求

- **代碼同步**：在修改現有功能、新增 API 或調整 UI 架構時，必須同步更新對應的文檔與註解。
- **及時清除過期資訊**：及時刪除已廢除的函式註解、過期的示範代碼及無效連結。
